# Протокол ESP Link v1

Плата: uPesy ESP32 Wroom DevKit, ESP32 WROOM, GPIO 2, LED active HIGH.

## Команды

Команды регистрозависимы, без завершающего `\n`, 1–20 печатных ASCII-байтов. Приложение удаляет пробелы и переводы строк с краёв перед отправкой. Неизвестная команда не переключает GPIO.

| Команда | Ответ | Действие |
| --- | --- | --- |
| `1` | `accepted:1`, позднее `done:1` | 3 импульса: 250 мс HIGH, 250 мс LOW между импульсами; в конце LOW |
| `on` | `ok:on` | HIGH |
| `off` | `ok:off` | LOW |
| `status` | `status:on`, `status:off` или `status:blinking` | Текущее состояние |
| `ping` | `pong` | Проверка связи |

Пока выполняется мигание, новые `1`, `on`, `off` возвращают `error:busy`. `status` и `ping` доступны. Неизвестная команда — `error:command`. Новую команду реализуйте в `CommandEngine::execute()` и `replyFor()`; быстрые кнопки находятся в `ContentView.swift`.

`done:1` означает завершение последовательности переключений GPIO в прошивке, **не оптическую проверку светодиода**. Если он неисправен или пин отличается, электроника этого не определяет.

## Bluetooth LE / GATT

UUID совместимы с форматом Nordic UART Service, но протокол приложения — текстовые команды ESP Link, а не произвольный UART-поток.

| Назначение | UUID | Свойства |
| --- | --- | --- |
| Service | `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` | — |
| RX, телефон → ESP32 | `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` | Write with response |
| TX, ESP32 → телефон | `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` | Notify + CCCD |

Порядок:

1. Найти advertising с Service UUID и подключиться.
2. Получить характеристики, включить Notify на TX, дождаться подтверждения подписки.
3. Записать в RX `auth:<12-символьный-токен>` — 17 байтов, помещается в стандартный ATT payload 20 байтов.
4. Дождаться `ready` на TX. Неверный токен → `error:auth`.
5. Записать `1` в RX. Ответы: `accepted:1`, затем `done:1`.

Каждая запись RX — отдельная команда, каждый Notify — отдельный ответ. Фрагментация и несколько команд в одном frame не поддерживаются. Длинные/непечатные BLE frames отбрасываются. GATT ACK подтверждает приём записи стеком, а не выполнение команды: ждите Notify.

Аутентификация действует только для текущего BLE-соединения. После разрыва нужно снова отправить `auth:`. Плата обслуживает один BLE-клиент; при разрыве снова начинает advertising. Уже начатое мигание продолжается, но новый клиент не получает подтверждение старой BLE-команды.

## Wi-Fi / HTTP

ESP32 создаёт WPA2-сеть `ESP32-Link-XXXX`. Пароль — токен устройства, IP — `192.168.4.1`, порт — `80`. Сеть рассчитана на два Wi-Fi-клиента. Интернет/мост в домашнюю сеть в этой версии не реализованы.

Все API-запросы требуют заголовок:

```http
X-Device-Token: <ваш-токен>
```

### GET `/api/status`

```json
{
  "name": "ESP32-Link-1234",
  "protocolVersion": 1,
  "busy": false,
  "led": false,
  "completedJob": 1
}
```

### POST `/api/command`

`Content-Type: text/plain; charset=utf-8`; тело — ровно одна команда, например `1`.

Для мигания HTTP `202`:

```json
{"reply":"accepted:1","job":1}
```

Для остальных успешных команд HTTP `200`, например:

```json
{"reply":"pong"}
```

Подтверждение мигания: опрашивать `/api/status`, пока `completedJob >= job`. Счётчик общий для команд обоих транспортов и сбрасывается при перезагрузке платы. Это не долговременный идентификатор: после перезагрузки нужно переподключиться и выполнить новую команду вручную.

Ошибки: `400` — неизвестная/неправильная команда; `401` — неверный токен; `409` — плата занята; `404` — неизвестный путь. Тело: `{"reply":"error:..."}`. CORS не включён; браузерная страница не должна управлять платой.

Пример PowerShell, не сохраняющий токен в файле:

```powershell
$token = Read-Host 'Device token'
Invoke-RestMethod -Uri 'http://192.168.4.1/api/status' -Headers @{'X-Device-Token'=$token}
Invoke-RestMethod -Uri 'http://192.168.4.1/api/command' -Method Post -ContentType 'text/plain' -Body '1' -Headers @{'X-Device-Token'=$token}
Remove-Variable token
```

Приложение проверяет связь по Wi-Fi раз в 3 секунды, во время мигания — опрашивает завершение примерно раз в 300 мс. При потере связи или таймауте команды не отправляются повторно автоматически. После перезапуска платы переподключитесь.

## Границы безопасности

- Случайный 12-символьный hex-токен создаётся при первом старте и сохраняется в NVS. Обычное переподключение питания не меняет его.
- USB Serial выводит токен после RESET. Физический доступ к USB фактически даёт доступ к управлению.
- Приложение сохраняет только последний токен в Keychain, не синхронизирует его через iCloud и не добавляет в журнал.
- **BLE link-level encryption/bonding не обязательны.** Токен защищает от случайной отправки команд, но не от радиоперехвата. Это не полноценный защищённый pairing.
- Wi-Fi защищён паролем WPA2, однако API использует HTTP без TLS; доверяйте только своей локальной сети и своим клиентам.
- Нет защиты от DoS, отзыва отдельных клиентов, обновления OTA или управления батареей. Ротация токена и безопасное provision-подключение не реализованы.
- Для реального изделия добавьте BLE Secure Connections/подходящий процесс pairing, отдельные ключи для клиентов, ротацию, TLS при сетевой работе и безопасное хранение секретов на ESP32. Не управляйте потенциально опасным оборудованием этим демонстрационным протоколом.
